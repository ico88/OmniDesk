# M5 — console, layout personali e TOTP

Console Windows WinForms/WebView2: stessa dashboard HTTPS e autorizzazioni server, origine obbligatoria `--server`, opzionale origine Mesh `--mesh` per link remoti nel browser esterno. Navigazioni interne limitate all'origine server; nessun bypass certificato, permessi browser negati, download dalla console principale disabilitati. Profilo WebView2 in LocalAppData, nessun segreto embedded. Richiede Evergreen WebView2 Runtime e fiducia CA LAN anche nel client Windows. Pubblicazione win-x64 riuscita anche sul runner Windows; esecuzione UI interattiva e firma ancora da collaudare.

```powershell
.\OmniDesk.Console.Windows.exe --server https://omnidesk.cricatania.it
```

Dashboard: layout personale (ordine/visibilità dei tre riquadri iniziali) persistente per utente, indipendente dal branding globale. API GET/PUT /api/dashboard/layout con {widgets:[devices,permissions,authentication]}, sottoinsieme ordinato senza duplicati. Nessuna metrica fittizia nei widget.

TOTP implementata usando i provider ASP.NET Identity, **disattivata per default** con OMNIDESK_TOTP_ENABLED=false. Per collaudo attivare true e ricreare il container API. Setup autenticato con password corrente, chiave generata da Identity, conferma TOTP prima dell'attivazione; login richiede password + codice o recovery code. Recovery code monouso e rotazione; disattivazione richiede password+TOTP. Un account già abilitato non può accedere con sola password se la feature viene disabilitata sul server: riabilitare il flag, mai bypassare MFA.

Le chiavi Authenticator e i recovery code vengono cifrati prima di persistere in AspNetUserTokens tramite DataProtection. Backup volume identity_keys obbligatorio: perdere le chiavi impedisce la decifratura. La cifratura protegge il DB separato dal volume, non da un amministratore host che possa leggere entrambi. Nessun servizio QR esterno; inserimento manuale chiave nell'app Authenticator. Segreti e recovery code mostrati in UI solo in memoria, cancellati quando si cambia scheda/logout; risposte no-store. Il codice TOTP ha la finestra di validazione del provider Identity; non implementato un registro anti-riuso dei codici TOTP. Lockout anche sulle riautenticazioni fallite.

API: POST /api/auth/totp/setup {password}; /enable e /disable {password,code}; /recovery-codes {password,code}; login {email,password,code?,recoveryCode?}. POST /api/auth/password {currentPassword,newPassword,code?}: aggiorna security stamp e rinnova la sessione corrente; altre sessioni invalidate alla richiesta successiva tramite controllo stamp sul DB. Tutte le mutazioni richiedono CSRF, auditate senza segreti. Recovery login disponibile; reset assistito in caso di perdita totale dei fattori ancora da progettare.

Fonti: [Identity MFA](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/mfa?view=aspnetcore-10.0), [WebView2 WinForms](https://learn.microsoft.com/en-us/microsoft-edge/webview2/get-started/winforms).

Hardening successivo: la rotazione dei recovery code aggiorna il security stamp nella stessa transazione dei codici e dell'audit. La sessione corrente viene rinnovata dopo il commit; le altre vengono invalidate alla richiesta successiva tramite controllo stamp sul DB, come per il cambio password. Richiede ancora password e TOTP validi. I codici precedenti inutilizzati sono invalidati; quelli nuovi restano monouso. Non modifica il flag TOTP, disattivato per default.

Gestione accessi dashboard: la schermata Utenti elenca account e ruoli globali, crea account usando i ruoli restituiti dal server (inclusi quelli personalizzati), crea gruppi dispositivi, assegna concessioni per gruppo/dispositivo e le revoca con conferma. Le concessioni sono additive: revocarne una non elimina ruoli globali o altre concessioni. Operazioni tramite API amministrative esistenti, con CSRF, autorizzazione globale `administration` e audit server; nessun nuovo permesso implicito. Nessuna modifica/eliminazione di ruoli globali o account introdotta in questo incremento. I gruppi sono disponibili per i successivi token enrollment.


Lifecycle account: `AspNetUsers.IsDisabled` distingue sospensione amministrativa dal lockout temporaneo. API/UI consentono sospensione, riattivazione, sostituzione dei ruoli globali e revoca delle sessioni web, tutte con autorizzazione globale administration e CSRF. La sospensione propria è negata; la rimozione dell'ultimo account abilitato con administration globale è negata. Un advisory lock PostgreSQL serializza le modifiche stato/ruoli e il server ricontrolla il chiamante dopo il lock. I ruoli locali non vengono cancellati. Audit e modifica account sono nella stessa transazione; modifiche conflittuali Identity tornano 409.

Cookie verificato contro stato account e security stamp a ogni richiesta: revoca, sospensione e cambio ruoli invalidano i cookie precedenti senza attendere il minuto del validatore periodico Identity. La riattivazione richiede nuovo login; gli account non vengono eliminati e lo storico audit resta integro. La revoca delle sole sessioni web non chiude sessioni remote autorizzate indipendenti.

Per sospensione, perdita capacità/ambito, revoca dispositivo o scadenza, il guard remoto controlla le sessioni ogni dieci secondi fra cicli (non un limite garantito di chiusura), persiste revocation_pending e ritenta la revoca tramite adapter. Conferma del motore e audit portano a revoked; errori restano pending. Riesame anche dopo creazione del link prima di consegnarlo. Test con fake, non attestazione di chiusura tunnel MeshCentral reale. Backup e restore full-stack/allegati sono provati nello smoke isolato. È implementata la retention dei soli eventi outbox consegnati, con soglia configurabile e audit; retention di ticket/allegati/audit, reset assistito password/MFA, cancellazione account e modifica dei permessi dei ruoli restano da sviluppare.
